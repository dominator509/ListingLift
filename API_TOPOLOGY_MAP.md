## Legend

| Symbol | Meaning |
|--------|---------|
| `✓` | Explicit schema/model defined |
| `INFERRED` | Contract inferred from route handler implementation |
| `MISSING` | Route handler references service but no route file exists |
| `SEED` | Scaffold route, service returns dry-run plan data |
| `LIVE` | Route calls real Prisma/third-party operations |

## 1. Auth & Session Layer

### 1.1 CSRF Token Generation
| Field | Value |
|-------|-------|
| **Route** | `POST /api/csrf/token` |
| **Auth** | Session required (`requireSession`) |
| **CSRF** | Not applicable (token issuer) |
| **Permission** | None (authenticated-only) |
| **Request Body** | None |
| **Response 200** | `{ ok: true, data: { csrfToken: string, expiresAt: Date } }` |
| **Error 401** | `SESSION_REQUIRED` |
| **Status** | `SEED` — generates CSRF token in-memory |
| **Runtime** | `csrf-protection-service.generateCsrfToken()` |

### 1.2 Signup
| Field | Value |
|-------|-------|
| **Route** | `POST /api/auth/signup` — INFERRED |
| **Auth** | Public |
| **Request Body** | `{ email: string, password: string (min 8), name: string, organizationName: string }` |
| **Request Schema** | `Zod` — `signupSchema` in `schemas/auth.ts` ✓ |
| **Response 200** | `{ ok: true, data: { sessionToken, session, user } }` |
| **Error 409** | `CONFLICT` — email already in use |
| **Error 400** | Validation errors |
| **Status** | `MISSING` — `auth-service.signup()` exists but no route handler |
| **Cookies** | Sets `ll_session` HttpOnly cookie |

### 1.3 Login

## 5. Sales Channels & External Orders

### 5.0 Shared Schema
All sales channel routes use `salesChannelNormalizationRequestSchema` (Zod, `schemas/sales-channel.ts`):
```
{ channelKey: string, mode: 'API'|'WEBHOOK'|'EMAIL_PARSER'|'MANUAL'|'CSV_IMPORT',
  payload: Record<string,unknown>, organizationId?: string, dryRun: boolean }
```

Enums for status tracking: `UNPAID|PENDING|PAID|REFUNDED|FAILED|MANUAL_CONFIRMED`,
`NOT_STARTED|TOKEN_SENT|PARTIAL|COMPLETE|FAILED`,

## 16. Auth Implementation Gap

The auth routes (`/api/auth/signup`, `/api/auth/login`, `/api/auth/logout`) are implemented as service functions in `server/auth/auth-service.ts` but have **no Next.js App Router route handlers**. They need route.ts files and endpoint wiring. The service functions are LIVE — they call Prisma for user creation, login verification, and session management.

All other routes are scaffolded (SEED) — they validate input and return dry-run plans but do not persist to the database.

---

## 17. Key Findings

1. **Auth routes missing**: 3 critical endpoints (signup, login, logout) are implemented in the service layer but have no route handlers. This is the most significant gap.

2. **All non-auth routes are SEED**: Every other route handler exists as a file but returns dry-run data. None persist to the database via Prisma — `codexNote` fields document what needs to be wired.

3. **CSRF protection is thorough**: Every authenticated mutation route includes `verifyCsrfForRequest()`. The CSRF token is generated per-session.

4. **Permission model is placeholder**: `assertPermission()` in `authorization-service.ts` is a no-op (`// Phase 3: placeholder — always allows`). The permission strings cataloged in `domain/permissions.ts` are not enforced.

5. **Webhook idempotency not implemented**: Stripe webhook route describes the idempotency gate in a note but does not implement it.

6. **Schema consistency**: All routes use explicit schemas (some Zod, some hand-rolled with `parse()` methods). No route infers contracts purely from implementation — all are documentable.

7. **Role-based permission map is defined**: 8 roles with their 24 permission assignments are cataloged in `domain/permissions.ts`, but the runtime enforcement layer is incomplete.
