## 2. Schema Drift Findings

### Critical (security-relevant)

| # | Finding | Route(s) | Impact |
|---|---------|----------|--------|
| 1 | **Zod validation failures return 500, not 422** | All routes using `mapServiceError()` | ZodError lacks `.code` property. `mapServiceError` doesn't check `instanceof ZodError`. All validation errors silently become `INTERNAL_SERVER_ERROR`. |
| 2 | **Auth routes return 400 for Zod failures, not 422** | `POST /api/auth/signup`, `/login` | `authError()` returns `auth_error` with fallback 400 for Zod errors — not consistent with the documented 422/VALIDATION_ERROR contract. |
| 3 | **Manual schemas accept any payload** | All 10 schemas in `upload.ts` and `security-hardening.ts` | Schemas like `uploadBatchIntakeRequestSchema`, `securityUploadProbeSchema` use `as string` casts — a `{ organizationId: 123, jobId: true }` passes silently. |
| 4 | **No Zod maxLength on email fields** | `signupSchema`, `loginSchema` | `.email()` validates format but not length. RFC 5321 limit of 254 chars is not enforced. |
| 5 | **No Zod maxLength on password inputs** | `loginSchema`, `signupSchema` | A 100K char password passes validation. Hash function downstream truncates, but memory/transport amplification risk exists. |

### Moderate (operational drift)

| # | Finding | Route(s) | Detail |
|---|---------|----------|--------|
| 6 | **`uploadCompleteRequestSchema` returns no `organizationId`** | `POST /api/uploads/complete`, `POST /api/admin/uploads/manual` | Route handlers access `input.organizationId` but the manual parser doesn't include it in its output. Causes TS error (line 16). |
| 7 | **`uploadBatchIntakeRequestSchema` returns no `token`** | `POST /api/uploads/public-intake` | Route handler accesses `input.token` but manual parser output has no token field. TS error (line 11, 22). |
| 8 | **`zoneEntries` cast on `securityUploadProbeSchema` output** | `POST /api/admin/security/upload-guard` | Handler does `body.zipEntries` but `parseJson(request, {})` returns type `{}` — TS error (line 12). |
| 9 | **Auth routes are LIVE, not MISSING** | `POST /api/auth/signup`, `/login`, `/logout` | API_TOPOLOGY_MAP.md says "MISSING" but route files exist and call real Prisma. Topology map is stale. |
| 10 | **`uploadFileMetadataSchema` has different field names** | Various upload components | Uses `{name, size, type}` but `UploadFileMetadata` interface uses `{fileName, mimeType, sizeBytes}`. `file-validation.ts` imports non-existent `allowedImageMimeTypes`. |

### Minor (documentation drift)

| # | Finding | Detail |
|---|---------|--------|
| 11 | `securityAuditEventDraftSchema` output lacks many fields | Service code accesses `organizationId`, `userId`, `eventType`, `controlArea`, `route`, `resourceType`, `resourceId` — none returned by the manual parser. |
| 12 | `stripeWebhookEventSchema` has no deep validation | Only validates `id` and `type` are strings. `data.object` and other fields pass through unvalidated. Accepts prototype pollution payloads. |

## 3. Validation Pattern Taxonomy

### Pattern A: Proper Zod (Recommended — ~40 routes)

```ts
export const signupSchema = z.object({
  email: z.string().email('Invalid email address'),
  password: z.string().min(8, 'Password must be at least 8 characters'),
  name: z.string().min(1, 'Name is required'),
  organizationName: z.string().min(1, 'Organization name is required'),
});
```
- Proper type enforcement, descriptive error messages
- Used in: `auth`, `quality-control`, `manual-approval`, `preview`, `sales-channel`, `delivery`, `client`, `rbac`

### Pattern B: Manual Parser (Weak — 10 schemas)

```ts
export const uploadBatchIntakeRequestSchema = {
  parse: (input: any) => {
    if (!input || typeof input !== 'object') throw new Error('Input must be an object');
    return { organizationId: input.organizationId as string | undefined, ... };
  },
};
```
- Only checks `typeof === 'object'`
- All fields use `as string` casts — no type enforcement
- Missing required fields pass silently (become `undefined`)
- Used in: `upload.ts`, `security-hardening.ts`, `stripe-billing.ts`

### Pattern C: No Validation (GET routes — ~8)

- `GET /api/uploads` — no body validation
- `GET /api/clients` — via `guardedGet()`
- `GET /api/admin/qa/verification-ledger` — no body
- `GET /api/jobs/:jobId/approval` — via `guardedGet()`
- Acceptable since GET requests carry no body

### Pattern D: No Schema At All (1 route)

- `POST /api/delivery/create-token` — parses body with raw `as` casts, no schema object at all. Validates nothing.

## 5. Zod Error Message Sanitization Audit

| Check | Result | Detail |
|-------|--------|--------|
| Implementation details in error messages | ✅ SAFE | All Zod error messages use static strings (`'Invalid email address'`, `'Name is required'`). |
| Regex/internals leaked | ✅ SAFE | No `.message` exposes regex patterns, field names leak, or stack traces. `mapServiceError` only forwards `error.message`. |
| CSRF errors in response | ✅ SAFE | CSRF errors have dedicated codes, no implementation leakage. |
| Auth errors in response | ✅ SAFE | `authError()` checks message patterns but only forwards the message string. |
| **Recommendation** | ⚠️ | The `mapServiceError` function should explicitly check `instanceof ZodError` to return 422 instead of 500. Currently ZodError messages are logged but returned as generic 500. |
